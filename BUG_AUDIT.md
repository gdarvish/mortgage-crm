## A1 — Auth, theme & shell


### A1-01 — `signOut` never clears loading state on error; user state not reset locally
- **Severity:** P1
- **Area:** Auth store
- **File:** src/stores/authStore.ts:83
- **Repro / Why it's a bug:** `signOut` sets `loading: true` then `await fbSignOut(auth)` but never resets `loading` and has no try/catch. If sign-out throws (offline, network error) the entire app stays in the `<AuthLoadingScreen />` forever because `ProtectedRoute` gates on `loading`. The success path relies on `onAuthStateChanged` to fire `loading: false`, but the error path has no recovery.
- **Proposed fix:** Wrap in try/finally and reset `loading: false` (and optionally `user: null`) in `finally`. Surface the error to the caller.

### A1-02 — Sign-in/Sign-up success path leaves `loading: true` until auth listener fires
- **Severity:** P2
- **Area:** Auth store
- **File:** src/stores/authStore.ts:48-69
- **Repro / Why it's a bug:** On success, the actions never set `loading: false` — they rely on `onAuthStateChanged` to do so. Between resolution of `signInWithEmailAndPassword` and the listener firing, `ProtectedRoute` will render `<AuthLoadingScreen />`. More importantly, `LoginPage` calls `navigate('/')` immediately after success; `ProtectedRoute` then immediately renders the loading screen until the listener runs, causing a visible flicker. If the listener never fires (e.g. emulator hiccup), the app is stuck.
- **Proposed fix:** Either explicitly `set({ loading: false })` in the success branches, or have `LoginPage` rely on the protected route to render once the listener fires (and remove the manual navigate).

### A1-03 — `initialize()` is recreated on every render; effect can re-subscribe on hot-reload / StrictMode double-mount
- **Severity:** P2
- **Area:** Auth lifecycle
- **File:** src/App.tsx:62-68, src/stores/authStore.ts:36
- **Repro / Why it's a bug:** `useAuthStore((s) => s.initialize)` returns a stable reference, so the effect runs once — fine. But the effect calls `initialize()` which calls `onAuthStateChanged` every time, with no guard against double-subscription. In React 18 StrictMode (which is enabled at main.tsx:33), the effect mounts → unmounts → mounts. Cleanup runs the previous `unsubscribe`, so we don't leak, but we DO miss any auth event that fires between the two mounts (rare but possible), and we definitely re-attach a Firestore listener twice if `initialize` were ever called twice (e.g. layout remount). More robust to make `initialize` idempotent.
- **Proposed fix:** Track `initialized` in the store and short-circuit subsequent calls, or move the subscription out of the component (eager top-level in `authStore.ts`).

### A1-04 — `useState(readStoredTheme)` runs synchronously on first render but `applyCssVars` fires only in a layout effect → FOUC
- **Severity:** P1
- **Area:** Theme system / FOUC
- **File:** src/theme/ThemeContext.tsx:57-63, index.html:1
- **Repro / Why it's a bug:** index.html has no inline script to set `data-theme` or background before React mounts. `body` background is hardcoded to `#faf9f7` in index.css. A user on the `night` theme (dark bg `#141210`) sees a bright cream flash on every full load until React mounts and `useEffect` runs `applyCssVars`. Worse: `applyCssVars` is in `useEffect`, not `useLayoutEffect`, so even after mount there's a paint between first render and the var application.
- **Proposed fix:** Add a small blocking inline script in index.html that reads `localStorage['crm-theme']` and sets `document.documentElement.dataset.theme` + `document.body.style.background` before paint. Move `applyCssVars` to `useLayoutEffect`.

### A1-05 — Theme CSS vars don't fully match Tailwind `@theme` — half the palette can't be themed via utilities
- **Severity:** P2
- **Area:** Theme system
- **File:** src/theme/ThemeContext.tsx:18-38, src/index.css:3-36
- **Repro / Why it's a bug:** `applyCssVars` writes 18 vars but `themes.ts` defines 28 fields (e.g. `warning`, `warningBg`, `info`, `infoBg`, `shadow`, `shadowHover`, `inputBg`, `pillBg`, `pillText`, `primaryText`). None of those will flip when the theme changes if the styling references the Tailwind `@theme` tokens directly. Also `@theme` in `index.css` doesn't declare tokens for `warning/info/shadow/inputBg/pillBg/pillText` at all, so Tailwind utilities like `bg-warning` won't even compile.
- **Proposed fix:** Sync the two: add all theme fields to both `applyCssVars` and the `@theme` block in `index.css`. Otherwise document the subset that's themable.

### A1-07 — VerifyEmailPage `checkVerified` does full-page reload, losing React Query cache & in-flight state
- **Severity:** P2
- **Area:** Auth / Routing
- **File:** src/pages/VerifyEmailPage.tsx:33-35

## A2 — Customers / Leads / Documents


### A2-01 — Bulk delete uses raw writeBatch and skips related-data cleanup
- **Severity:** P0
- **Area:** Customers / bulk actions
- **File:** src/pages/CustomersPage.tsx:98-113
- **Repro / Why it's a bug:** `handleBulkDelete` calls `writeBatch(db).delete(...)` directly. The confirm message promises deletion of "all related data" (documents, mortgages, tasks, etc.), but no related collections are touched — they become orphans pointing at non-existent customer ids. The same issue applies to single-customer delete via `customerService.delete` (CustomerDetailPage line 213).
- **Proposed fix:** Move bulk delete behind a service method that deletes related documents/mortgages/tasks/messages/commissions/loan_tracks in batches (or via Cloud Function), the same way `convertToCustomer` uses `writeBatch`. Also invalidate `['documents']`, `['tasks']`, etc., not just `['customers']`.

### A2-02 — Bulk delete only invalidates `['customers']`, leaving `customers/infinite` pages stale
- **Severity:** P1
- **Area:** Customers / cache
- **File:** src/pages/CustomersPage.tsx:106
- **Repro / Why it's a bug:** The page reads from `useCustomersInfinite` whose key is `['customers','infinite', opts]`. `qc.invalidateQueries({queryKey: ['customers']})` should match by prefix and works, but `useUpdateCustomer` / `useDeleteCustomer` and single-customer delete (CustomerDetailPage line 224) invalidate only `['customers']` — they do NOT invalidate the `['documents']` list cache or other related caches that the deleted customer fed into (e.g. DocumentsPage shows orphan rows after delete).
- **Proposed fix:** After any customer mutation, also invalidate `['documents']`, `['tasks']`, `['messages']`, `['commissions']`, `['leads']` (the converted-from side), and `['dashboard']`.

### A2-03 — Lead convert silently drops `score` and `notes`
- **Severity:** P1
- **Area:** Leads / convert flow
- **File:** src/services/leadService.ts:98-112
- **Repro / Why it's a bug:** The customer payload created from a lead omits `lead.notes` (could be mapped to `customer.notes`) and the `score` is discarded entirely. The confirm dialog promises "תיק לקוח חדש" but the user loses content they typed on the lead card.
- **Proposed fix:** Copy `notes: lead.notes ?? null` into the new customer payload and either persist `score` on a `lead_score` field or include it in `notes`. Optionally also persist a `converted_from_lead_id` field on the customer for traceability.

### A2-04 — Convert button on Kanban card fires while drag pointer-up still active
- **Severity:** P2
- **Area:** Leads / DnD
- **File:** src/pages/LeadsPage.tsx:209-231
- **Repro / Why it's a bug:** `onPointerDown` is stopped, but `onClick` will still fire when a click immediately follows a drag-no-move (e.g. accidental click on the "המר" button at the end of a tiny drag). The drag activation distance is 5px, so any pointerdown-pointerup under 5px triggers `onConvert` even if the user intended to drag.

### A2-05 — Lead `useLeads` filter passes raw `search` but service uses substring on already-fetched docs after `orderBy`
- **Severity:** P2
- **Area:** Leads / search
- **File:** src/services/leadService.ts:30-46 + src/pages/LeadsPage.tsx:254-258, 326-331
- **Repro / Why it's a bug:** `useLeads({search})` makes a new query keyed on `search`, but the page ALSO filters the same `leads` array client-side at line 326 using `.includes(search)`. This double-filters: server returns leads matching `search` (case-insensitive substring on name/phone), and client filters again with case-sensitive `.includes(search)` (no `.toLowerCase()`), so any uppercase Hebrew/Latin search will fail.
- **Proposed fix:** Either rely on the server filter only and skip the client `.filter` (preferred — also yields stable react-query cache), or remove the `search` argument from the query and only filter client-side with `.toLowerCase()` matching.

### A2-06 — Lead search by `search` argument is part of query key — every keystroke creates a new query
- **Severity:** P2
- **Area:** Leads / performance
- **File:** src/hooks/queries/useLeads.ts:12-19 + LeadsPage.tsx:255
- **Repro / Why it's a bug:** Each character typed in the search input triggers a fresh Firestore round-trip (cache miss because key includes `search`). For a Hebrew search of 10 chars this means 10 reads, each fetching all leads.
- **Proposed fix:** Drop `search` from query key, do client-side filter only, or debounce the input.

### A2-07 — Customers status count uses loaded customers only, but page filters by status server-side

### A3-01 — calculateMonthlyPayment returns NaN when annualRate is negative and months > 0 in edge formula; also returns Infinity for very small negative rate combos
